# Безопасная регистрация

Регистрация создаёт учётку и первый секрет. Ошибки здесь живут всё время жизни аккаунта: слабый пароль, роль из браузера, почта без проверки, массовое создание ботов.

Защитный промпт: имена угроз здесь, чтобы их закрыть. Пошаговых атак нет.

## Уязвимости

| Угроза | Что происходит |
| --- | --- |
| Роль, `isAdmin` или скидка приходят из клиента | Человек назначает себе права при создании аккаунта |
| Пароль сохраняется как есть или быстрым хешем | Утечка базы сразу даёт входы |
| Почта не подтверждена, но уже может сбрасывать пароль и платить | Чужой адрес привязывают к аккаунту |
| Ответ «такая почта уже есть» без лимита | Каталог пользователей собирается перебором |
| Нет лимита на создание аккаунтов | Боты забивают базу и рассылают мусор |
| Лишние поля тела запроса пишутся в модель | Mass assignment: в учётку попадают поля, которых нет в форме |
| Пароль уходит по HTTP или остаётся в логе запроса | Секрет оседает в сети или в access-log |

## Сделать

1. Белый список полей регистрации. Роль, флаги верификации, баланс, тариф и id задаёт только сервер.
2. Те же правила пароля и хранение, что в `login.md` и `password-storage.md`.
3. Пока почта или телефон не подтверждены одноразовым кодом, не отправлять на них сброс пароля и не открывать выплату и смену контакта. Код - как в `10-business/email-verification.md`.
4. Ответ регистрации сделать одинаковым там, где это не ломает продукт: «если адрес можно использовать, мы отправили письмо». Если продукт обязан говорить «адрес занят», компенсировать это лимитом и антиавтоматизацией, не разной скоростью ответа.
5. Лимит регистраций с одного источника и антиавтоматизация на форме. Капча - запасной слой, не единственный контроль.
6. Не логировать тело запроса с паролем. Не отдавать пароль назад в JSON «для удобства».
7. Согласие с условиями хранить как факт (версия документа и время), если продукт это требует. Галочку с клиента не считать криптографическим доказательством, просто записью согласия.
8. После регистрации не сажать человека в сессию, пока обязательная проверка контакта не пройдена, либо сажать в урезанную сессию без чувствительных действий.

## Промпт

```text
Усиль регистрацию в этом репозитории. Стек не меняй без нужды.

Найди создание пользователя: форма, API, импорт, OAuth-дорегистрация.
Закрой назначение прав из клиента, слабое хранение пароля, недоказанный контакт, массовую регистрацию ботов и запись лишних полей в модель.

Сделай так:
- сервер принимает только белый список полей; роль, баланс, тариф, флаги верификации клиент задать не может;
- пароль хранится медленным хешем по правилам password-storage, не в открытом виде;
- чувствительные действия ждут подтверждения почты или телефона одноразовым кодом;
- ответ по возможности не сообщает, занят ли адрес; если сообщает - стоит лимит попыток;
- есть лимит созданий аккаунта и защита от автоматической регистрации;
- пароль не попадает в логи, аналитику и ответ API;
- новая сессия не получает права на оплату, смену контакта и админку до завершения обязательных проверок.

Не пиши эксплойты и списки payload-ов. Если регистрации нет - пропусти и напиши почему.
В конце: файлы и оставшиеся ручные решения (текст писем, провайдер капчи).
```

## Готово, когда

- [ ] Клиент не задаёт роль и флаги доверия
- [ ] Пароль не хранится в открытом виде и не быстрым хешем
- [ ] Контакт подтверждается до чувствительных действий
- [ ] Есть лимит на создание аккаунтов
- [ ] Пароль не светится в логах и ответе
