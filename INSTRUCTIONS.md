# Инструкция для ИИ

Прочитай этот файл целиком. Потом пройди промпты в этой же папке и закрой ими проект, который тебе дали вместе с инструкцией. Карта файлов лежит в `README.md`. Её достаточно просмотреть, исполнять нужно этот файл и файлы промптов.

Это защита. Имена уязвимостей нужны, чтобы их не оставить в коде. Не пиши эксплойты, payload-ы, словари, перехват трафика, обход подписи, подбор паролей и страницы, которые бьют по чужому сайту. Если откроешь внешний cheat sheet, бери только защитные меры. Каталоги обхода фильтров пропускай.

Не утверждай, что проект прошёл PCI DSS, ISO, GDPR, 152-ФЗ или аудит. Не ослабляй уже стоящий контроль. Не коммить и не печатай секреты. Не выдумывай продукт там, где правила денег и ролей непонятны: спроси.

## Что считать проектом

Проект - код, который тебе открыли для правки, не эта библиотека промптов. Файлы промптов не переписывай. Если кода нет, так и напиши и остановись. Не создавай новое приложение «чтобы было что защищать».

## Шаг 1. Инвентарь

Кратко зафиксируй:

- стек и фреймворк;
- где вход, регистрация, сессия, админка;
- где деньги, корзина, вебхуки;
- где файлы, исходящие HTTP-запросы, импорт;
- где роли и организации;
- где письма, коды, SMS;
- где вызовы модели, если есть;
- где CI, Docker, зависимости.

Не читай боевые базы и не выписывай персональные данные в отчёт.

## Шаг 2. Какие файлы брать

Обойди все `*.md` в подпапках. `README.md` и этот файл не являются промптами.

У каждого промпта в начале есть блок полей: `id`, `priority`, `applies_when`. Файл обязателен, если в инвентаре есть хоть один смысл из `applies_when` или соседняя функция без этого контроля опасна. Иначе пометь `не применимо` одной фразой. Сомнение при `priority: critical` решается в сторону «применить».

Внутри файла читай таблицу угроз, список «Сделать» и блок «Промпт». Блок «Промпт» - задание. Остальное - критерии, чтобы не закрыть угрозу наполовину.

## Шаг 3. Порядок

Иди по риску, не по алфавиту. Список ниже задаёт приоритет. Файлы, которых в нём нет по имени, всё равно прочитай: в папках есть соседние темы.

1. `09-data/secrets.md` - убрать секреты из дерева и логов до остальных правок.
2. `04-transport/tls.md` - канал, без которого пароль и cookie не защищены.
3. Вход: `password-storage.md`, `login.md`, `registration.md`, `password-reset.md`, `mfa.md`, `passkeys.md`, `credential-stuffing.md`, `oauth-oidc.md`, `saml.md`.
4. Сессия: `session.md`, `jwt.md`, `logout.md`.
5. Права: `csrf.md`, `authorization.md`, `idor.md`, `multi-tenant.md`, `privileged-actions.md`.
6. Ввод и файлы: вся папка `06-input`, затем `07-files`.
7. Деньги: вся папка `03-payments`, плюс `10-business/business-logic.md`.
8. API: `08-api`, заголовки, кэш, фреймы и CORS из `04-transport`.
9. Данные и журналы: остальные файлы `09-data`, включая ключи, случайность и отказ при сбое.
10. Почта, лимиты, гонки, зависимости, настройки, база, сеть, CI, контейнеры, ИИ-функции.

Файл из позднего шага можно сделать раньше, если без него текущая правка дырявая. Пример: оплата сразу тянет вебхук, цену на сервере и секреты шлюза.

## Шаг 4. Как править один промпт

- Сначала найди существующий код фреймворка. Включай его защиту, не пиши вторую рядом и не выключай встроенную.
- Закрывай угрозу на сервере. Прятать кнопку в интерфейсе можно только вместе с сервером.
- Не логируй пароль, токен, cookie, полный номер карты, CVV, сырое тело вебхука.
- Тесты добавляй только если в проекте уже есть тесты. Проверяй отказ и инвариант: лишнее поле не меняет роль, повтор вебхука не отгружает дважды, чужой id не отдаёт объект. Не складывай в репозиторий набор атакующих строк.
- Не трогай боевой кластер, боевые ключи и боевые данные. Не проверяй «жив ли ещё ключ» запросом к чужому API.
- Секрет, который уже был в git, считай утёкшим. В отчёте укажи имя переменной и файл, не значение. Напиши, что человек должен отозвать ключ.

Если правка ломает непонятное бизнес-правило, останови этот пункт и спроси. Не выбирай молча, можно ли суммировать купоны и кто имеет право поддержки входить в клиента.

## Шаг 5. Отчёт

В конце один отчёт. Без живых секретов и персональных данных.

```text
Инвентарь
- стек
- какие функции нашёл

Сделано
- id промпта - что закрыто - файлы

Не применимо
- id - почему

Нужен человек
- сертификат, отзыв ключа, порог лимита, юридический объём PCI, бэкапы вне репозитория

Не закрыто
- id - что мешает
```

Не пиши «проект безопасен» и «соответствует стандарту». Пиши, какие пункты закрыты в коде, а какие остались на человека.

## Запрещено

- Эксплойты, PoC, payload-ы, инструкции перехвата и обхода.
- Ослабить проверку, чтобы тест стал зелёным.
- Общий пароль, чёрный ход, отладочный вход без пароля.
- Секреты в коде, в примере конфига, в отчёте и в логе.
- Новый сбор отпечатков браузера «для безопасности».
- Самодельный шифр и самодельная подпись JWT.
- Выключить аудит зависимостей, CSRF фреймворка или проверку сертификата ради тишины.
