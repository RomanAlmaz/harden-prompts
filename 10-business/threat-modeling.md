# Модель угроз и сценарии злоупотребления

Новая функция без вопроса «что будет, если это позовут не из формы» получает проверки в конце, когда их уже некуда вставить. Этот файл не требует отдельного документа на каждый чих и не заменяет остальные промпты.

Защитный промпт: имена угроз здесь, чтобы их закрыть. Пошаговых атак нет.

## Уязвимости

| Угроза | Что происходит |
| --- | --- |
| Доверили клиенту цену, роль или признак «уже проверено» | Правило живёт только в браузере |
| Не назван актив: деньги, чужие файлы, админка | Контроль из других файлов не к чему применить |
| Сценарий злоупотребления не отличается от обычной ошибки | Лимит и право забывают |
| Защиту откладывают «после запуска» | В проде остаётся первый вариант без проверок |

## Сделать

1. Для новой функции коротко записать: какие данные, кто ими пользуется, что нельзя делать без права, что считается злоупотреблением.
2. Граница доверия - сервер. Всё, что пришло из браузера, очереди и вебхука, недоверенное, пока файл соответствующего промпта не закрыт.
3. По этому списку открыть нужные промпты: вход, права, ввод, файлы, оплата. Не писать отдельный «общий защитный слой» вместо них.
4. Не составлять пошаговые сценарии обхода. Писать требуемый отказ: «чужой заказ не читается», «вторая отгрузка не создаётся».

## Промпт

```text
Перед крупной новой функцией назови актив, действующих лиц и отказы, которые сервер обязан дать.

Не пиши пошаговые атаки. Для каждого отказа укажи, какой промпт этой базы его закрывает, и примени тот промпт.
Если функция маленькая и уже покрыта одним файлом, не раздувай документ: напиши, какой файл применён.

Не объявляй проектирование законченным, пока названные отказы не закрыты в коде или не отданы человеку.
```

## Готово, когда

- [ ] У новой функции названы актив и обязательные отказы
- [ ] Отказы закрыты конкретными промптами, а не общим абзацем
- [ ] Нет пошаговых сценариев обхода
